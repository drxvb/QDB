# quickdb-native

`NativeStore` implements `quickdb_api::Store` (`0.1.0` pre-release, `MIT OR Apache-2.0`): relational rows, vectors and directed edges in one embedded directory, with no server and no external C++ toolchain. Bundled SQLite `3.54.1` (`rusqlite` `0.43`, `libsqlite3-sys` `0.40.0`) stores schemas, rows, edges and authoritative vectors; an in-crate Rust HNSW graph handles vector search and saves checksummed snapshots. For a runnable quickstart, see `README-example.md` at the workspace root (`examples/readme_quickstart.rs`).

## Layout, locking and durability

- **`quickdb.sqlite` (WAL mode):** holds schema tables, one physical table per logical table (`TEXT COLLATE BINARY`, secondary indexes on indexed columns), little-endian `f32` vector blobs with a per-index revision and random write nonce, a 16-byte `store_id`, and directed edges indexed on `(src, rel, dst)` and `(dst, rel, src)`. Prepared statements are cached (capacity 128) with a 30-second busy timeout and `SQLITE_DBCONFIG_ENABLE_QPSG` enabled on every connection (`0` re-prepares and `0` sorts on SQLite `3.54.1`). Indexed `IntRange` and `TextPrefix` `select` queries sort covering-index IDs before fetching row payloads; indexed `TextPrefix` uses a binary byte range.
- **Locking and readers:** `Store::open` takes an exclusive non-blocking OS lock (`quickdb.lock`, via `std::fs::File::try_lock`) before opening SQLite; a second writer fails at once with `Error::Backend`. `open_read_only` takes no writer lock, rejects writes and `flush()`, reads rows and edges live from SQLite, and serves vectors committed as of open (rebuilding missing, invalid or stale snapshots in memory only). `NativeStore` is `Send`, not `Sync`. Keep stores on local disk; OS locks may not hold on network file systems.
- **Snapshots and recovery:** `<index>.hnsw` stores a version marker, `(store_id, revision, nonce)` header, `bincode` (`1.3.3`, unmaintained `RUSTSEC-2025-0141`, informational) serialized HNSW graph and vectors, and a trailing 4-byte CRC32 checksum. Open verifies the checksum before deserializing, rejects payloads over 8 GiB (excluding the checksum), and validates graph invariants. Missing, oversized, damaged, foreign or stale snapshots rebuild from SQLite in ascending ID order; `index_rebuilds()` reports recoveries during open.
- **Flush and sync:** bulk mode (`sync_each_write = false`) uses `PRAGMA synchronous = NORMAL`, not `OFF`. `flush()` compacts indexes whose dead nodes exceed one fifth of physical nodes (`ids.len() / 5`), writes and fsyncs `<index>.hnsw.tmp.<pid>`, atomically renames it to `<index>.hnsw`, runs `PRAGMA synchronous = FULL` with `PRAGMA wal_checkpoint(TRUNCATE)` (SQLite syncs the database file; a blocked checkpoint returns `Error::Backend`), and fsyncs the store directory on Unix. With `sync_each_write = true`, SQLite stays on `FULL` and writes flush before returning. If an HNSW update panics after SQLite commits, the in-memory batch rolls back and marks that index stale, rejecting operations on it and `flush()` until reopen rebuilds it.

## Vector search and index build

- **Graph and metrics:** HNSW uses deterministic geometric layers (up to level 24) and diversified pruning (`2 * m` links at layer 0, `m` above; `m` is clamped to at least 2 and `ef_construction` to `max(m, 16)`). Cosine vectors and queries are normalized in `f64` (zero vectors have cosine distance `1.0`); `L2` stores raw `f32` values and computes squared Euclidean distance.
- **Build, SIMD and experimental switches:** after seeding the first 256 vectors sequentially, `upsert_vectors` inserts in deterministic batches of up to 64 on up to 8 worker threads (`available_parallelism().min(8)`), searching the frozen pre-batch graph with a default 12.5% construction breadth margin (`ef + ef / 8`); the graph does not depend on worker count. On `x86_64`, SSE prefetching issues up to 4 hints per float vector by default and AVX2 kernels match scalar 8-accumulator rounding; `L2` indexes of at most 256 dimensions whose coordinates are whole numbers in `0..=255` also keep an in-memory `u8` cache (rebuilt on open, never serialized). Three experimental opt-in switches exist and are off by default (default graph unchanged): `QUICKDB_BUILD_FLOAT_OFF=0` for first-visit neighbour prefetch, `QUICKDB_BUILD_MARGIN_PCT` for construction breadth margin, and `QUICKDB_BUILD_FMA=1` for an AVX2 fused multiply-add distance kernel. Replacing a vector appends a physical node and redirects the active map; dead nodes stay traversable until `flush()` compacts above one fifth dead nodes, rebuilding that index inside `flush()`. Deleting a row excludes it from `knn_filtered` without removing its vector.
- **Unfiltered `knn`:** uses exact scoring when active vectors are at most 512 or `ef_search` covers all physical nodes. Otherwise it descends upper layers greedily and walks layer 0 best-first, doubling breadth if dead nodes leave fewer than `k` live hits. Results are ordered by distance then ascending ID.
- **Filtered `knn_filtered`:** probes up to 256 evenly spread physical positions (skipping dead nodes) in 128-ID SQLite primary-key batches to estimate selectivity `s`. Let `ef = max(ef_search, k)` and `N` be live vectors:
  - **Lazy graph walk** (when `s >= max(0.02, sqrt(15 * ef / N))`): walks layer 0 expanding 8 frontier nodes per batched SQLite probe, starting at 40% of `ef` when `s < 0.1` or 60% otherwise (at least `k`), widening by 4× up to physical node count. Fitted on SIFT only.
  - **Streaming bitmask and bounded exact path** (otherwise, or if the lazy walk returns fewer than `k` hits): streams matching IDs from SQLite into a 1-bit-per-node mask and keeps live positions only up to `exact_up_to = max(1024, floor(2 * sqrt(ef * N)))`, releasing that buffer once exceeded so only the mask stays in RAM. Up to `exact_up_to` live matches use exact scoring; more run a bitmask-filtered graph walk (widening by 4×) and, if still short, score set mask bits in batches of at most `exact_up_to`, merging top `k` per batch.

## Graph traversal

`Store::k_hop` always runs breadth-first search in Rust (`k_hop_bfs`) at every depth, reading neighbor IDs from SQLite's covering indexes (`edges` and `edges_in`). The start node is marked seen immediately so cycles never return it. Once a depth reaches the remaining `limit` budget, `k_hop_bfs` switches to a max-heap retaining only the smallest distinct remaining IDs at that depth and stops expanding deeper hops once `limit` is filled; retained visited, frontier and result memory stays bounded by `O(limit)` (`71.7 MB` to `2.0 MB` on a `2,000,000`-edge star with limit `1`; SQLite still scans frontier edges). `k_hop_sql` (recursive SQL) remains public for comparisons and is not called by `Store::k_hop`.
